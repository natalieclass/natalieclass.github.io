P.S. Coffee Shop — back end restructure

Narrative

The artifact for enhancement one is the back end of P.S. Coffee Shop, a web application I built at Brookdale Community College in 2022. I built this coffee shop website for a friend who hoped to open one in the future. It uses HTML, CSS, JavaScript, and jQuery on the front end, Node and Express on the back end, and MySQL for storage. Customers can create an account, sign in, browse syrups and sauces, edit their information, and leave feedback. For this category I picked the server files: psapp.js, psrouter.js and psservices.js.

I picked this artifact because the back end was the weakest part of the project, thus it was the best place to show how much my skills have changed since 2022. psservices.js was one of my original files that opened the database connection, held all five API endpoints, and wrote every SQL query. After reviewing it, I found problems I’d never noticed while the site was running like the /Cart route pointed at a file that doesn’t exist; every endpoint returned a 201 whether it worked or failed; repeated error blocks; and debug statements were printing user passwords to the console.

What shows my skills now is the structure, the security work, and the tests. The back end is split into routes, controllers, services and repositories, with all the SQL in the repositories. Passwords are hashed with bcrypt. The credentials moved into environment variables instead of sitting in a public repo. Sign-in became a POST so the password isn’t in the URL, and input is checked before it reaches the database. The tests are the part I’m happiest with. I couldn’t have written them before, because the logic, the SQL and the HTTP handling were all in the same function.

I planned to meet outcomes three, four and five, and I think all three are covered. Outcome four is the layered structure, the connection pool, the middleware, async/await instead of callbacks, and the tests. Outcome five is the bcrypt hashing, the credentials out of the source code, sign-in out of the URL, the validation, and the parameterized queries. Two smaller things I’m glad I caught belong there too: a 500 now returns a generic message instead of the raw error that leaked table names, and sign-in says the same thing whether the email is wrong or the password is, so nobody can use the form to find registered emails. Outcome three is the trade-off. One endpoint now spans five files instead of one, which is real added complexity, but it’s what makes the code testable. I’d also add outcome two, which I didn’t claim in Module One, since writing a README for another developer is professional communication.

The longest part was re-familiarizing myself with the project, trying to understand what I did with a lack of comments. Also, setting up the connections and looking through the files to see all the necessary changes. I eventually learned that with time, patience, and a checklist, trying to divide and conquer rather than tackle the problem all at once helped me debug and create the necessary code so I could begin the work. I moved one endpoint at a time through every layer, which kept the application working instead of broken. When I copied the register function to write the login function, for code reusability and to finish that task, I noticed that it is better to just write out the code. I couldn’t reuse that code block because the logic was different. Register rejects you if the email already exists, and login rejects you if it doesn’t. I also couldn’t hash what the user typed and compare the two hashes, because bcrypt uses a different salt every time, which is what bcrypt.compare is for.

The schema I wrote in 2022, discovering it wouldn’t build on current MySQL, was a bit of a learning curve. It failed with a foreign key error because my Employee table used employeeID and password together as the primary key. I haven’t worked with MySQL in a while and the application was slightly different in terms of the buttons, and setting up the connection took some time. The original code focused on the front end and didn’t focus too much on code readability, security, and correctness. Something I would do differently is focus on security and code efficiency, and add more comments so someone in the future could understand.
